# Agent mechanical design over the MCP

An agent designs well on a PCB because the design is text, the intent is
declarative, and a design-rule check gives a fast pass/fail loop. Mechanical
CAD has none of those by default. This spec gives the Waffle Iron MCP the three
properties: geometry that is answerable by tool call, references and
parameters that carry intent across rebuilds, and a rule check that returns a
list of violations. It then covers the two things an agent needs around that
loop: a view it can read, and a sketcher it can drive to parity with the UI.

Source: the goal document "Waffle-iron MCP: Agent Mechanical Design Spec"
(claude.ai artifact `051dd7ae-e9a3-45d0-8967-c6bfed1184d6`, 2026-10-02). It
asked that each capability be mapped onto what exists, with pushback where the
architecture suggests a better route. §13 collects the pushback.

Owner crates: `kernel-v2` (Q1–Q5), `waffle-types` (N1, P1, K1 types),
`feature-engine` (N2, P2–P4, K2–K5, L1, E1–E3), `sketch-solver` (S1–S2),
`wasm-bridge` (every tool), `app` (V1–V4, S3), `test-harness` (A1–A2),
`relay` (manifest only).

Status: **design, nothing landed.** Written 2026-10-03 from a survey of the
tree at `233e1728`. Three increments it depends on are specified elsewhere and
are not repeated here: persistent edge and vertex ids (D0), planar section
(D1d) and measurement functions in expressions (D2), all in
`specs/drawings_and_mbd.md`. Material and mass (M1 there) is referenced by Q3.

Fillet, chamfer and shell remain deferred. Nothing here depends on them, and
§8 says what the machining rule does without them.

## 1. Scope

In scope, in the goal document's priority order:

1. **Queryable geometry (Q).** Distance, angle, clearance, interference, mass
   properties, section, wall thickness, edge and vertex listings. Every answer
   is numbers plus stable references, never only a picture.
2. **Stable semantic references (N).** Names an agent gives to bodies, faces,
   edges and vertices that survive rebuilds, fail loudly when they cannot be
   resolved, and work in every query and operation.
3. **Design intent as parameters (P).** Units on parameters, a document-level
   table, every numeric feature field expression-driven, and the table
   readable as structured data.
4. **Mechanical rule check (K).** A `rules_check` tool over selectable rule
   sets stored as data, returning violations with severity, location,
   offending references and a reason.
5. **Part library (L).** Purchased parts as parametric scripts that publish
   named mating features, plus STEP import with named features attached after.
6. **Agent-legible views (V).** Deterministic captures with isolation,
   semantic colouring and labels, from the 3D viewport or a sketch.
7. **Sketcher parity (S).** Every sketch operation reachable by tool call,
   solver state queryable, and a sketch regression corpus.
8. **Electromechanical integration (E).** A plain-text interface file, pad and
   connector frames from the board, keep-outs both ways, cable routes checked
   by length and bend radius, board outline back to KiCad.
9. **Acceptance (A).** The auger doser, and a corpus of recorded agent tasks
   that the test harness replays headless.

Out of scope: FEA and dynamics, photorealistic rendering, sheet-metal rules
(there is no sheet-metal feature to check, §13), thread modelling as geometry
(a helical sweep is its own spec per `specs/b6_general_sweep.md`), and any
PMI or drawing output (covered by `specs/drawings_and_mbd.md`).

## 2. What exists today, and what is missing

The survey behind this section is in three parts: the MCP tool surface, the
reference and parameter layers with the kernel's queries, and the sketcher,
viewport, KiCad, assembly and assay machinery. File references below are to
the tree at `233e1728`.

### 2.1 Already in the tree

- **54 MCP tools** behind one generated manifest
  (`relay/src/waffle_mcp_relay/agent-tools.manifest.json`, regenerated by
  `app/scripts/gen-agent-manifest.mjs` from the CI-pinned schema golden). Tool
  definitions in `app/src/lib/agent/tools/*.js`, engine implementations in
  `crates/wasm-bridge/src/tools/*.rs`. One implementation serves both the
  browser page and the native host plus viewer (`specs/waffle_server_mode.md`
  §4.12), so every tool added here lands in both transports.
- **`body_measure`** returns exact B-Rep volume and area with a `method`
  field that says `exact` or `mesh` (`crates/wasm-bridge/src/tools/inspect.rs:107`).
  The bounding box is from the render mesh, chord-inscribed on curved faces.
- **`GeomRef`** (`crates/waffle-types/src/geom_ref.rs:11`) with anchor,
  selector (`Role`, `Signature`, `Query`, `Position`), policy and cross-tab
  scope. `Selector::Query` with `TopoQuery` filters is the durable way to say
  "the largest face whose normal is +Z" today.
- **Face Pids and the operation journal** (`crates/kernel-v2/src/arena.rs:135`,
  `journal.rs`) carry face identity through booleans, read through
  `face_provenance`. Not addressable from a saved reference; D0 adds
  `Selector::Pid`.
- **Parameters** (`specs/parameterized_designs.md`, landed): a real parser,
  a per-Part table, 19 expression-driven fields, cycle detection, loud
  errors, `parameters_set` and `expression_evaluate`.
- **Sketch solver** (`crates/sketch-solver/src/solver.rs`): LM with a QR
  rank computation, so `dof` is real, and `OverConstrained { conflicts }`
  names the offending constraints.
- **27 constraint types and 7 entity types**, all authorable through
  `sketch_create`.
- **Mate connectors** on parts (`Operation::MateConnector`) and in assemblies
  (`connector_add` with `part_connector | geom_ref | frame`), re-derived from
  live geometry every evaluation. Scripts publish connectors with
  `ctx.mate_connector` and name faces or edges with `@output name: face`.
- **A six-kind mate solver** (`crates/feature-engine/src/assembly_solver.rs`).
- **Custom feature scripts** (`Operation::Script`, Rhai) with a two-entry
  built-in library (`gear`, `sprocket`). This is the mechanism a part library
  is built on.
- **Exact STEP import** (SI5 C6): an analytic shell becomes a first-class
  kernel solid, so `entity_axis` and booleans work on it.
- **KiCad link** C1–C5: board outline and cutouts as exact derived features,
  footprint instances from a board STEP, a mate connector per mounting hole,
  `entity_meta` for board and component records. Drill diameters are parsed
  and dropped; pad positions are parsed but not exposed.
- **3D sketches** with `Fillet` entities and exact chain length from
  `sketch3d_get`; polygon sweeps along 3D line-and-arc paths (B6).
- **`viewport_view`** with seven named views and region framing;
  **`viewport_capture`** returning a PNG of the user's current view.
- **The assay runner** with subprocess isolation, CPU-time budgets, a
  categorizer, an exact-volume lattice oracle, and the prospector's
  signature-group-and-shrink loop, all domain-agnostic.

### 2.2 Missing, or defective

Listed in the order the increments repair them.

1. **No body-to-body geometry at any layer.** No distance, closest points,
   interference, clearance, section (as data), wall thickness, centroid or
   inertia. `KernelIntrospect` has no such method; the assembly solver never
   consults geometry, so two mated instances can interpenetrate unnoticed.
   The only inter-body relation is AABB overlap. There is no `edge_list` or
   `vertex_list` tool, and `TopoSignature.length` is the chord between an
   edge's endpoints, not its arc length (a full circle reports 0).
2. **Two reference defects that make face references unreliable today.**
   kernel-v2 returns an empty signature for every non-planar face
   (`crates/kernel-v2/src/adapter.rs:333`), so `SurfaceType{cylindrical}` can
   never match and every curved face in a boolean result is attributed to
   operand A. And `face_list` hands a roleless face a signature whose only
   field is the face index in `adjacency_hash`, which the resolver never reads
   (`crates/wasm-bridge/src/face_refs.rs:66`, `crates/modeling-ops/src/diff.rs:160`);
   the reference resolves to the first created face with a "0.0%" warning.
   This is the ICR-3 limit recorded in `projects/14-agent-link/PLAN.md` and it
   bites every imported STEP body, which has no roles at all.
3. **Silent rebind is the default.** `ResolvePolicy::BestEffort` carries
   `#[default]`, and under it a failed role, an unmatched query, a sub-0.5
   signature match and an out-of-tolerance position all bind to some face
   with a warning string (`crates/feature-engine/src/resolve.rs:223-341`).
   Nothing promotes the warning to an error. A local sketch on a face reads
   cached plane numbers and never re-resolves the face
   (`crates/feature-engine/src/context.rs:324`), so it stays put when the
   face moves. Datum planes do re-resolve and fail loudly on a non-planar
   base; sketches should behave the same.
4. **No way to name an entity.** `feature_rename` and `body_rename` set
   display names only. A face or edge can be named only by a script's
   `@output`. There is no `Selector::Pid`, so a name has nothing stable to
   alias until D0 lands.
5. **Parameters carry no unit and nothing checks dimensions.** `25deg` as a
   depth is 25 mm; `1in` as an angle is 25.4 degrees. The table is per Part;
   an Assembly has none and tabs cannot share. Gear and sprocket parameters,
   second-direction depth, sketch-region boundaries and assembly transforms
   take no expressions. `parameter_overrides` on an instance is declared and
   not applied.
6. **No rule check of any kind.** A whole-repo search found no DFM,
   interference, fastener, thread, hole, wall-thickness or keep-out code. The
   only shipped checks are two closed-form planetary gear rules and the
   kernel's own validity oracles.
7. **No hole feature.** The `Operation` enum has no `Hole`; a hole is a cut
   extrude of a circle. A fastener check has nothing to read.
8. **No part library.** The examples panel holds two whole documents; the
   script library holds two sketch generators; there is no catalogue, no
   standard-parts table, no published-geometry concept beyond connectors.
9. **`viewport_capture` has one knob.** No camera, size, isolation, section,
   style, colouring or labels. The image is the user's live canvas at the
   user's size, theme, selection and hover state, antialiased, so two
   captures are not comparable. Body visibility, section view and sketch mode
   exist only on `window.__waffle`.
10. **Sketch editing is wholesale.** No incremental sketch tool. Trim, offset
    and sketch fillet are browser JavaScript with no Rust twin
    (`app/src/lib/sketch/tools.js`, `offset.js`); extend does not exist;
    projection is reachable only through the raw `Sketch` operation. The
    over-constrained highlight in the UI is a constraint-count heuristic that
    overrides the solver (`app/src/lib/engine/store.svelte.js:4053`), and the
    under-constrained marker flags unreferenced points rather than the null
    space. Conflict indices are dropped on the `keep` path and index the
    filtered driving list.
11. **Every sketch in the 321-case assay corpus has zero constraints.** The
    solver has no corpus.
12. **The KiCad link is one-way.** Nothing writes back. Pad positions, drill
    diameters, component heights and keep-outs do not reach the mechanical
    side. There is no shared interface file. A round cable on a 3D route is
    not expressible (B6 refuses a circle section; pipe refuses a 3D path).

## 3. Architecture

```
┌──────────────────────────────────────────────────────────────────────────┐
│ app (Svelte / three.js)                                                  │
│  AgentRender.svelte — offscreen pass: isolate, style, colour_by, labels  │
│  sketch tools call engine ops (trim/extend/offset/fillet) via bridge     │
└───────────────────────────────▲──────────────────────────────────────────┘
                                │ tool results (JSON), legend + label coords
┌───────────────────────────────┴──────────────────────────────────────────┐
│ wasm-bridge tools                                                        │
│  measure_*  entity_list  entity_name  rules_check  sketch_edit           │
│  sketch_solve_state  parameters_get  library_*  interface_export         │
└───────────────────────────────▲──────────────────────────────────────────┘
                                │
┌───────────────────────────────┴──────────────────────────────────────────┐
│ feature-engine                                                           │
│  names: BTreeMap<String, GeomRef>   (aliases over Selector::Pid)         │
│  rules::{RuleSet, Violation, check}  — reads kernel queries, never meshes│
│  sketch_ops::{trim, extend, offset, fillet, project}  (pure, on Sketch)  │
│  library: Rhai scripts + data tables, publish connectors                 │
│  kicad: pads, drills, heights → interface file                           │
└───────────────────────────────▲──────────────────────────────────────────┘
                                │ KernelMeasure trait (waffle-types)
┌───────────────────────────────┴──────────────────────────────────────────┐
│ kernel-v2                                                                │
│  measure::{distance, closest_points, mass_properties, thickness}         │
│  interference = yang Intersect on operand copies + volume                │
│  arc_length on edges; signatures for curved faces                        │
└──────────────────────────────────────────────────────────────────────────┘
```

Four rules hold the layering:

- **Rust answers, the app draws.** Every query returns numbers and
  `GeomRef`s. The capture tool returns an image plus a legend that maps every
  colour and label back to a reference, so the image and the queries share
  one vocabulary.
- **The rule check runs in the engine.** It is Rust compiled to WASM and
  native, so it runs in the browser page and in the headless host with one
  implementation. This answers the goal document's open question directly:
  not "browser or server", both, because it lives below either.
- **Names are aliases, not a second identity system.** A semantic name
  points at a `GeomRef` whose selector is a Pid. The kernel's journal is the
  truth about what survived a rebuild; the name table just labels it.
- **Loud by default for agents.** Every reference an agent authors is
  `Strict`. A drift the resolver would once have papered over is a typed
  error that names what changed.

Units: tools keep today's convention (meters and degrees on the wire,
mm-space for expressions), stated in every tool description by
`app/src/lib/agent/tools/common.js`.

## 4. Q — Queryable geometry

Owner: `kernel-v2` (new module `measure`), `waffle-types` (trait),
`wasm-bridge` (tools).

### 4.1 Trait

```rust
pub trait KernelMeasure {
    fn distance(&self, a: &Entity, b: &Entity, opts: &DistanceOpts)
        -> Result<Distance, KernelError>;
    fn mass_properties(&self, solid: SolidId, density: Option<f64>)
        -> Result<MassProperties, KernelError>;
    fn interference(&mut self, a: SolidId, b: SolidId)
        -> Result<Interference, KernelError>;
    fn thickness(&self, solid: SolidId, opts: &ThicknessOpts)
        -> Result<Thickness, KernelError>;
    fn edge_length(&self, edge: EdgeId) -> Result<f64, KernelError>;
}

pub enum Entity { Vertex(VertexId), Edge(EdgeId), Face(FaceId), Solid(SolidId),
                  Axis(Line3), Point(Point3) }

pub struct DistanceOpts { pub along: Option<Vector3> }   // None = minimum

pub struct Distance {
    pub value: f64,
    pub points: [Point3; 2],              // closest point on a, on b
    pub on: [Option<EntityRef>; 2],       // the face/edge/vertex each point lies on
    pub method: Method,                   // Exact | Mesh { chord_bound: f64 }
}

pub struct MassProperties {
    pub volume: f64, pub centroid: Point3,
    pub inertia_at_centroid: [[f64; 3]; 3],  // volume-weighted; × density if given
    pub principal: ([f64; 3], [[f64; 3]; 3]),
    pub mass: Option<f64>,
    pub method: Method,
}

pub struct Interference {
    pub kind: InterferenceKind,           // Disjoint { gap } | Contact { faces } | Overlap
    pub volume: f64,                      // 0 unless Overlap
    pub region: Option<SolidId>,          // the overlap solid, for faces/section/capture
    pub closest: Option<Distance>,        // for Disjoint and Contact
}

pub struct Thickness {
    pub min: f64, pub at: Point3, pub between: [EntityRef; 2],
    pub samples: usize, pub spacing: f64, // honest about what was sampled
    pub method: Method,
}
```

Angles are not a kernel method: `angle(a, b)` is computed in the tool layer
from `entity_axis` and planar normals that already exist.

### 4.2 Increments

1. **Q1 — distance and closest points.** Two tiers, both reported.
   *Seed:* a BVH over each operand's render tessellation (the same
   `tessellate` output the app draws), closest triangle pair by branch and
   bound, O(n log n). *Refine:* when both carrier faces are analytic
   (plane, cylinder, cone, sphere, torus — every `Surface` the arena holds),
   run Newton on the two-surface closest-point system from the seed, clamped
   to the faces' trimming loops through the existing in/out predicates. The
   result is `Exact` when refinement converged inside both faces and `Mesh`
   with a chord bound (`RENDER_CHORD_TOLERANCE_REL × extent`) otherwise, which
   is the case for mesh-backed imports. The `along` option projects both
   operands onto the direction and reports the gap along it; the same seed,
   a 1D refine. Vertex, edge, axis and point entities are the degenerate
   cases of the same routine.
2. **Q2 — interference.** AABB reject first (`solid_aabb` is conservative).
   Then run the yang pipeline's `Intersect` on arena copies of the two
   solids, as a query, never a feature: the result solid is held in the
   query's own arena scope and dropped after the answer unless the caller
   asks to keep it as a body for inspection. A non-empty result is
   `Overlap` with its exact volume (`solid_volume`) and the overlap region's
   faces mapped back to operand faces through `face_provenance`. An empty
   result is `Disjoint` with the Q1 distance filled in, never a silent
   nothing (memory trap: a disjoint Intersect today leaves no solid and says
   so to no one). A typed Stage-0 coplanar refusal between the operands is
   reported as `Contact { faces }` naming the coplanar pair: touching faces
   are a legitimate assembly state, and the kernel's loud wall is exactly the
   detector for them.
3. **Q3 — mass properties.** `signed_volume` already integrates exactly over
   the B-Rep by the divergence theorem; the first and second moments are the
   same integral with polynomial integrands one and two degrees higher, over
   the same face parameterizations. `density` comes from M1's material table
   when it lands; until then `mass` is `None` and the tool says so. Method is
   `Exact` for arena solids and `Mesh` for imports, as `body_measure` does
   now.
4. **Q4 — section as data.** D1d (`section_with_plane`) is the kernel piece.
   This increment is only the tool: `measure_section { body_ids | all,
   plane }` returning per body the cap loops as 2D analytic curves in the
   plane's frame, each loop's area, and the loop edges' source faces. The
   half-space boolean is the one that already exists.
5. **Q5 — wall thickness.** From every vertex of the render tessellation (and
   the centroid of every triangle above a size threshold), cast a ray along
   the inward normal and take the first hit on the same solid, then refine
   the hit on the analytic surface pair as in Q1. Report the minimum, where
   it is and which two faces bound it. Report `samples` and `spacing` so the
   consumer knows a feature narrower than the spacing could be missed. A
   `ThicknessOpts.spacing` lets a rule ask for a denser sample. This is the
   medial-axis question answered by sampling; an exact medial axis is not in
   scope and the result never claims to be one.
6. **Q6 — listings and lengths.** `entity_list { body_id, kind: face | edge |
   vertex, filter? }` with full geometric content per entity: the fixed
   signature from N0, arc length for edges (`edge_length`, exact for lines,
   circles and ellipses, sampled at chord tolerance for SSI curves), position
   for vertices, and `axis` from `entity_axis` when there is one. The
   existing `face_list` becomes the `face` arm.

### 4.3 Tools

| tool | inputs | result |
|---|---|---|
| `measure_distance` | `a`, `b` (any `EntityRef`: a `GeomRef`, a name, a body id, an axis or a point), `along?` | `Distance` |
| `measure_angle` | `a`, `b` (planar faces, axes, straight edges) | `{degrees, kind: between_normals \| between_axes}` |
| `measure_interference` | `a`, `b` (bodies, or instance paths in an assembly), `keep_region (false)` | `Interference` |
| `measure_mass` | `body_id`, `density_kg_m3?` | `MassProperties` |
| `measure_section` | `body_ids?`, `plane` | loops, areas, sources |
| `measure_thickness` | `body_id`, `spacing?` | `Thickness` |
| `entity_list` | `body_id`, `kind`, `filter?` | entities with signatures, lengths, axes |

In an assembly every tool accepts instance-scoped references
(`RefScope.instance_path`) and transforms operands into world space by the
solved placement before measuring. `body_measure` stays as it is and gains a
`centroid` field from Q3.

### 4.4 Oracles

- **Distance.** For every pair of primitives the exact-membership lattice can
  describe (`crates/test-harness/src/assay/exact_membership.rs`), the
  closed-form distance between two spheres, a sphere and a plane, two
  parallel cylinders, and a point and each primitive must match Q1 to
  `TAU_MODEL`. For every corpus body, the distance from a body to itself
  translated by `d` along x is `d − extent_x` to the mesh chord bound.
- **Interference.** Two unit boxes offset by `(0.5, 0, 0)` overlap with
  volume exactly 0.5; offset by `(1, 0, 0)` they are `Contact` naming the two
  coplanar faces; offset by `(1.5, 0, 0)` they are `Disjoint` with gap 0.5.
  Over the corpus, `interference(A, A)` has volume `volume(A)`.
- **Mass.** Centroid of every primitive and every boolean result matches the
  lattice's own moment integrals; the inertia tensor of a box matches the
  closed form; rotating a solid rotates its principal axes.
- **Thickness.** A shelled box (two boxes, Subtract) reports its wall to
  chord tolerance; a plate reports its thickness at every sample.

## 5. N — Stable semantic references

Owner: `waffle-types`, `feature-engine`, `wasm-bridge`, `kernel-v2` (N0).

### 5.1 N0 — Fix the two reference defects (prerequisite, bug-class)

These are repairs, not features, and they come first because every later
increment resolves references.

1. **Curved-face signatures.** `face_signature` in `kernel-v2/src/adapter.rs`
   fills `surface_type` (`cylindrical | conical | spherical | toroidal`),
   `area` (exact for the analytic surfaces, the same integrals Q3 uses),
   `centroid`, `bbox`, and `normal` as the outward normal at the centroid
   for every surface the arena holds. Consequences: `SurfaceType` filters
   work on real bodies; `assign_boolean_roles` no longer ties every curved
   face to operand A.

   **Full-revolution faces: axis descriptor, no point normal** (amended
   2026-10-03, during review of the N0 branch). "The outward normal at the
   centroid" is not available for a face that sweeps all the way round its
   axis: its area centroid lies ON the axis, where the normal is undefined
   and the direction from the axis to the centroid is f64 summation rounding
   — measured 3.1e-17 m off a cylinder's axis, so changing that cylinder's
   height from 2 to 2.0001 swung the reported centroid 58° round the axis
   and flipped the normal from (−0.50, −0.87, 0) to (−1.00, −0.03, 0). A
   fingerprint exists to be stable, so such a face reports `normal: None`
   and a centroid snapped exactly onto the axis (which IS its area centroid,
   and pins its axial position), and carries the rotation-invariant
   `AxisDescriptor` instead: the sign-canonicalised axis direction, the
   radius / half-angle / minor radius the surface holds, and how far the face
   reaches along the axis. Every cylinder, cone, sphere and torus face
   carries the descriptor, full turn or not, read straight off the analytic
   surface. Partial faces additionally keep the projected centroid and the
   normal there, both well defined; the presence of `normal` is what says
   which kind of centroid a signature carries, so a consumer that needs a
   point ON the face must require both. `signature_match` scores the
   descriptor (direction sign-free, then the radii and the extent relative);
   `Filter::NormalDirection` excludes a face with no normal, `Selector::
   Position` still resolves by nearest centroid deterministically, and
   `DepthMode::UpTo` refuses such a face rather than extruding to a plane
   through its axis.
2. **Roleless fingerprints.** `face_list` and every other agent-facing
   path call `face_geom_refs` with `fingerprint_roleless: true`, and
   `signature_similarity` refuses a zero-weight signature with
   `ResolutionFailed { reason: "signature carries no geometry" }` instead of
   scoring 0.0 and binding to the first face. The ICR-3 limit closes. The
   index-only fallback goes away on the EDGE path too (`build_edge_entries`
   minted the edge index in `adjacency_hash` and nothing else): an edge ref
   now carries the length and centroid of its own render polyline, or the
   resolver would refuse every viewport edge pick.

Oracle: for every corpus case, every face in `face_list` resolves back to
itself through `resolve_geom_ref_live`; for every imported STEP fixture, the
same.

### 5.2 N1 — Entity names

```rust
// feature-engine FeatureTree
pub names: BTreeMap<String, NamedRef>,

pub struct NamedRef {
    pub target: GeomRef,                   // selector: Pid when available, else Query/Role
    pub kind: TopoKind,
    pub created: Provenance,
}
```

Names are `[A-Za-z_][A-Za-z0-9_]*` and may be dotted: `motor_mount.top_face`
names a face inside the body named `motor_mount`. The body part of a dotted
name is a body name (`body_names`, today's `body_rename`), so existing body
names become the first segment for free. A name resolves through
`resolve_geom_ref` with `Strict` policy. Every tool argument typed `EntityRef`
accepts a name string in place of a `GeomRef` or body id; every result that
carries a `GeomRef` also carries `name` when one points at that entity.

Resolution preference inside `target`: `Selector::Pid` (D0) when the entity
has one, else the `Query` that identified it at naming time, carried as a
fallback and used only when the Pid is gone; the fallback's use is reported
as `resolved_by: "query"` so the agent knows the primary identity was lost.

Tools:

| tool | inputs | result |
|---|---|---|
| `entity_name` | `target: EntityRef`, `name` | `{name, geom_ref}`; `NameTaken`, `InvalidName` |
| `entity_unname` | `name` | `{}` |
| `names_list` | `body_id?` | `[{name, kind, geom_ref, resolves: bool, resolved_by}]` |

Names live in the Part's tree and save with the document (serde-defaulted,
additive, no reader bump). Deleting the feature that introduced an entity
leaves its name in place and `resolves: false`, so the agent sees the hole
rather than losing the record.

**The reader floor DID move — to v7.** "No reader bump" above is wrong, and
the format's own rule says why (`docs/FILE_FORMAT.md` §13.3): a bump is
needed for "any change old readers cannot parse — which includes new
constraint/selector/`PlaneDefinition` *variants*". The `names` FIELD is
additive and defaulted, but every entry in it stores a `Selector::Pid`, and
`Selector` is a serde-tagged enum, so a v6 reader given a named document
fails with a raw unknown-variant error instead of the clean `FutureVersion`
message. D0 landed the variant without writing one and left exactly this
note (`specs/drawings_and_mbd.md` §4, "Still open"); N1 is the increment
that writes one. `FORMAT_VERSION` and `MIN_READER_VERSION` are both 7, in
`save.rs` and `app/src/lib/engine/format.js` together. A document with no
names is byte-identical to a pre-N1 one (the key is omitted), which is why
the corpus still loads — `corpus_backcompat` is the pin.

**The dotted path is a label; the identity is the stored reference.** The
map key is the name as written (`plate.top_face`), and the body segment is
checked against the body's display name when the name is ASSIGNED — never
again. A body renamed afterwards leaves a dotted name that still resolves
(its pid did not move) but whose first segment has drifted, which
`names_list` shows by reporting the owning body's *current* display name in
a `body` field next to each entry. The alternative — rewriting labels from
inside `rename_body` — would make a user's body rename fail on an agent's
name collision, and a label is not worth that.

**A body's name IS its display name.** `entity_name` with a `{"type":"body"}`
target routes to `body_names` (the mechanism `body_rename` already owns)
rather than opening a second record of it, which is what §5.2's "bodies where
not already present" asks for. The two share ONE namespace: a name taken by
a body's display name is `NameTaken` for an entity and vice versa, because a
body name is the first segment of every dotted entity name in it. For the
same reason `names_list` reports body names too, with `kind: Solid` and no
`geom_ref`. A body display name that is not an identifier (the derived
"Base plate", "Extrude (2)") cannot be a dotted first segment, and the
refusal says so and names the body rather than inventing a segment.
Features keep `feature_rename`: a feature is not a `GeomRef`.

**`NamedRef` carries a `fallback`, and `resolved_by` says which answered.**
`target` is the pid; `fallback` is the reference as the caller authored it,
stored only when a pid replaced it. `names_list`'s `resolved_by` is `pid`
(the stored pid answered), `selector` (the kernel had no identity for this
entity when it was named — a mesh-backed import) or `query` (the pid is gone
and the authored reference answered, which rebinds by geometry). The last
case carries a warning naming the lost id, so the agent is told rather than
just handed an answer.

**Names are not garbage-collected, deliberately** — including on feature
delete, where `body_names` and `provenance` ARE collected. §5.2 asks for
exactly this: the hole is the information.

**Refusals are typed at the tool layer, and checked again in the engine.**
`engine_call` collapses every engine error into `Internal` (ICR-2), and a
taken name is an ordinary thing for an agent to hit, so `entity_name` parses
the name, checks the namespace and checks the dotted segment itself and
answers `InvalidName` / `NameTaken` / `NameNotFound` /
`ReferenceNotResolved`. `Engine::set_entity_name` re-checks the grammar, the
uniqueness and the body segment, so a host that bypasses the tool layer
cannot store an unchecked name; such a refusal is then `Internal`, which is
right — it is a broken invariant, not a user error.

**Names reach arguments through two doors.** `MeasureOperand` (Q1's `a`/`b`,
the only `EntityRef`-shaped argument today) gains a `{"type":"name"}` arm, and
`require_body` — the one chokepoint every body-scoped tool already goes
through — accepts a body's NAME in place of its id and returns the id, so
`body_measure`, `face_list`, `measure_mass`, `measure_interference`,
`export_stl`, `body_rename` and `names_list` all take a name for free with no
second code path. The id is tried FIRST, which settles the one collision
possible: a body's display name is free text and can be spelled like another
body's `"{uuid}/{tag}"` id. The one namespace is enforced in both directions —
`entity_name` refuses a name a body's display name holds, and `body_rename`
refuses a `new_name` an entity name holds — so a string cannot come to mean
the entity in a `{"type":"name"}` operand and the body in `require_body`.
(A rename in the UI is deliberately not blocked on an agent's label, so a
hand-made document can still hold both; `names_list` lists both entries.)
"Every result that carries a `GeomRef`" is `face_list`, whose entries gain
`name`.

### 5.3 N2 — Loud resolution for agents

1. Every `GeomRef` an agent authors through a tool is stored with
   `policy: Strict`; the tool layer sets it when the caller omits it. User
   picks in the viewport keep `BestEffort` for now (the UI shows warnings;
   the agent cannot see them).
2. A `Strict` failure during a rebuild is `EngineError::ResolutionFailed`
   with a structured payload: `{ref, name?, reason: NoMatch | Ambiguous {
   candidates } | PidGone { last_seen_feature } | ScopeMissing}`. It is the
   feature's error, routed to `ModelDelta.errors[].kind` as
   `{"type": "ResolutionFailed", ...}`.
3. Local sketches re-resolve their plane face every rebuild, as
   `OffsetFromFace` datum planes do, and fail loudly on a non-planar or
   missing face. The cached numbers remain the solve-time frame for
   unchanged faces so determinism holds.

Oracle: the D0 identity oracle (rebuild twice, Pid map identical) extended
with names: after a no-op edit every name resolves to the same Pid; after a
parameter edit that keeps topology, the same; after an edit that deletes the
named face, `resolves: false` and the feature that referenced it reports
`PidGone`, never a different face.

## 6. P — Design intent as parameters

Owner: `feature-engine` (`expr.rs`, `params.rs`, `types.rs`), `file-format`,
`wasm-bridge`.

1. **P1 — units on parameters.** `DesignParameter` gains `unit: Option<Unit>`
   (`Length | Angle | Count | Ratio`) and `comment: Option<String>`. The
   evaluator tracks a dimension through arithmetic (length × length is an
   error where a length is expected; `deg` tags angle; a unitless literal
   adopts the context's dimension) and a dimension mismatch at an assignment
   site is a typed per-parameter error. `rad` joins the unit suffixes.
   `tan` near its pole and non-finite intermediates become errors, closing
   the two soft spots found in the survey (`min(1/0, 5)` passes today).
2. **P2 — document-level table.** `Document.parameters` alongside the per-Part
   tables; a Part's expression resolves local first, then document. An
   Assembly tab reads the document table, and `Instance.parameter_overrides`
   is applied: a Part instanced with overrides is rebuilt with those values
   under its own key, which is what the goal document's `spring_od = tube_id
   - 1.5 mm` needs when the tube and the spring are separate Parts.
3. **P3 — every numeric field.** `GearParams`, `SprocketParams`,
   `SecondDirection::Blind.depth`, assembly `translation_m` and connector
   `offset_m` gain `*_expr` siblings on the same optional-sidecar pattern.
   Sketch `region` boundaries re-derive from the solved sketch when a
   variable changes (closing `specs/parameterized_designs.md` §6's first
   limitation).
4. **P4 — measurement functions.** D2 as specified: `distance(a, b)`,
   `angle`, `volume`, `area`, `length`, `radius`, `mass`. Arguments accept N1
   names. A parameter that reads geometry acquires a rebuild dependency on
   the referenced feature; cycles are typed errors.
5. **P5 — read the table as data.** `parameters_get` returns the full table
   (`id, name, expression, unit, value, comment, error, depends_on[],
   used_by[]`), the two dependency lists derived from the parser (which
   requires the parser to produce an AST rather than evaluate as it parses;
   P1 makes that change). `parameters_set` echoes `expression` and accepts a
   partial update mode `merge: true` so an agent can set one parameter without
   re-sending the table.

Oracle: the existing `params.rs` suites plus: `depth_expr = "25deg"` is a
typed error; `angle_expr = "1in"` is a typed error; a document parameter
edited in the Assembly tab rebuilds both Parts that read it; a per-instance
override produces two different solids from one Part tab.

## 7. K — Mechanical rule check

Owner: `waffle-types` (types), `feature-engine` (new module `rules`),
`wasm-bridge` (tool), `file-format` (storage).

### 7.1 Data model

```rust
pub struct RuleSet {
    pub id: String,                          // "fdm-default", "m3-fasteners", user ids
    pub name: String,
    pub rules: Vec<Rule>,
    pub applies_to: Applies,                 // All | Bodies(Vec<EntityRef>) | Tagged(String)
}

pub struct Rule {
    pub id: String,
    pub kind: RuleKind,
    pub severity: Severity,                  // Error | Warning | Info
    pub params: BTreeMap<String, Value>,     // expressions allowed, mm-space
    pub enabled: bool,
}

pub enum RuleKind {
    Interference { min_clearance },                 // assembly, all pairs
    MinWall { thickness },
    MinFeature { size },                            // smallest cylinder radius, slot width, boss
    Overhang { build_dir, max_angle_deg, min_area },
    Bridge { build_dir, max_span },
    HoleDiameter { build_dir, shrink_mm },          // vertical printed holes come out small
    SharpInternalCorner { min_radius },             // concave planar-planar edges with no fillet
    PocketReach { max_depth_to_width },
    FastenerClearance { standard: Fit },            // reads Hole features (K3)
    FastenerEngagement { min_turns, max_turns },
    FastenerHeadClearance,
    KeepOut { zones },                              // from E2
    CableRoute { min_bend_radius, max_length },     // from E3
    Script { source_id, entry },                    // a Rhai rule over the query API
}

pub struct Violation {
    pub rule: String, pub severity: Severity,
    pub message: String,                            // plain language, with the numbers
    pub measured: Value, pub limit: Value,
    pub location: Point3,
    pub refs: Vec<GeomRef>,                         // offending entities, with names
    pub bodies: Vec<String>,
}

pub struct CheckReport {
    pub rule_sets: Vec<String>, pub violations: Vec<Violation>,
    pub checked: usize, pub skipped: Vec<Skipped>,  // rules that could not run, with why
    pub method_floor: Method,                       // the weakest method any rule relied on
}
```

Rule sets are **document data**, stored under `Document.rule_sets` (additive,
`x-` fallback preserved for unknown rule kinds) so an agent can read, edit and
author them, which is the goal document's second open question answered
"yes". Default sets ship as JSON in `feature-engine/rules/*.json` and are
copied into the document on first use so a document is self-describing.
Tags (`Applies::Tagged`) are a per-body string set alongside `body_names`, so
"printed parts" and "machined parts" are declared once.

### 7.2 Increments

1. **K1 — framework and the geometric rules.** Types, storage, the tool, and
   every rule that needs only Q: `Interference`, `MinWall`, `MinFeature`,
   `Overhang`, `HoleDiameter`, `SharpInternalCorner`, `PocketReach`.
   `Overhang` classifies each face by the angle between its outward normal
   and `-build_dir`: planar faces exactly, curved faces by sampling the
   normal over the face at chord density and reporting the worst sample's
   location. `Bridge` needs the downward planar face's footprint tested
   against support below it, which is a Q1 distance from each footprint
   sample to the rest of the body along `build_dir`; it lands in K1 too.
   `SharpInternalCorner` finds every edge whose two faces meet concave and
   are both planar, which is every internal corner in a kernel with no
   fillets: the rule says "this corner needs a radius of at least r" and the
   agent's remedy is to design the corner as a drawn arc, which is how
   fillets are authored today.
2. **K2 — `rules_check` tool.** `{rule_sets?: [id] (all enabled), bodies?,
   instance_paths?, severity_floor?}` → `CheckReport`. Runs in the engine on
   the open tab; in an Assembly tab `Interference` is all pairs of placed
   instances (AABB-pruned) and every other rule runs per Part through
   `RefScope`. `rules_get` / `rules_set` read and write the sets. The report
   is deterministic for a given document (violations sorted by severity, then
   rule, then body, then location).
3. **K3 — `Hole` feature and fastener rules.** `Operation::Hole { params:
   HoleParams }` with `HoleParams { placement: Vec<Point on face>, spec:
   HoleSpec }`, `HoleSpec = Simple { d, depth } | Clearance { standard, size,
   fit } | Tapped { standard, size, depth } | Counterbore { .. } |
   Countersink { .. }`. The feature executes as the cut extrudes it implies
   today, with `Role::Named` faces (`bore`, `seat`, `cone`) and a connector
   on the axis. It exists so a fastener rule has a spec to read and so a
   hole in a derived KiCad board (E1 drills) is the same thing as a hole an
   agent designs. Tables: ISO 273 clearance, ISO 4762 / 4017 / 7380 heads,
   ISO 965 tap drills and thread pitches, DIN 934 / ISO 4032 nuts, as JSON
   data in `feature-engine/tables/`. Rules: `FastenerClearance` checks a
   hole's bore against its spec's fit; `FastenerEngagement` finds the screw
   instance mated to the hole's connector and computes thread turns from
   the screw's length minus the stack it passes through (a Q1 distance along
   the axis); `FastenerHeadClearance` checks the head's cylinder against
   neighbouring bodies with Q2.
4. **K4 — scripted rules.** `RuleKind::Script` runs a Rhai entry with a
   read-only `ctx` exposing the Q tools and `names`, returning violations.
   This is how a user adds a shop-specific rule without a kernel change, and
   how the sheet-metal and machining families grow when their features exist.
5. **K5 — UI.** A Checks panel listing violations, clicking one frames and
   highlights its `refs`; the toolbar shows the count. The same `CheckReport`
   the tool returns.

### 7.3 Oracles

Each rule has a fixture pair: a document that violates it in exactly one
place and the same document with one parameter changed that passes. The
harness asserts the violation's `refs` resolve to the intended entities by
name and that `measured` matches an independent computation. The report over
the assay corpus with the default FDM set is pinned as a golden (count per
rule per case), so a kernel change that moves a classification is visible.

## 8. L — Part library

Owner: `feature-engine` (scripts, tables), `wasm-bridge` (tools), `app`
(browser panel).

The mechanism exists: a Rhai feature script with `@param`s, `@output`
bodies, named faces and `ctx.mate_connector`. A library part is such a script
plus a data table. Nothing new is needed in the kernel.

1. **L1 — catalogue.** `feature-engine/scripts/library/<family>/<part>.rhai`
   with a `library.json` index: family, part, params with units, published
   connectors (name, meaning), source of dimensions. First families, driven
   by the doser: metric socket-head and button-head screws, hex nuts,
   washers (ISO 4762 / 7380 / 4032 / 7089, from the K3 tables), 60x and 68x
   ball bearings, the JGB37-520 gear motor family (body, shaft with D-flat,
   mounting bolt circle, encoder housing), JST XH and PH headers and housings
   (mating face, pin 1), a bar load cell (TAL220 class) with its two bolt
   patterns, heat-set inserts. Every part publishes connectors named for
   their meaning: `shaft`, `mount_1..n`, `mating_face`, `pin_1`, and names
   its faces (`bore`, `flange`).
2. **L2 — tools.** `library_list { family? }` returns the index with params
   and connectors; `library_insert { part, args, arg_exprs, name? }` adds the
   source if absent and the feature in one undo step and returns its
   connectors; in an Assembly tab it also creates the instance and returns
   the instance's `part_connectors`. `script_source_add { library }` keeps
   working for the existing two.
3. **L3 — STEP parts with named features.** After `import_step` (exact tier),
   an agent names faces with N1 and adds connectors with `connector_add` or
   a `MateConnector` feature as today; L3 adds `part_publish { connectors:
   [{name, geom_ref}] }` which is the batch form, and stores a sidecar
   `published` block on the `ImportedBody` so a re-import of the same STEP
   (same `content_hash`) keeps the names. For a mesh-tier import, curved
   faces cannot carry axes, and the tool says so in the result rather than
   fitting one.
4. **L4 — browser panel.** The Examples browser gains a Library tab over the
   same index, inserting a part into the open tab.

Oracle: every library part builds on the real kernel, is watertight, and its
published connectors sit where the datasheet says (asserted numerically per
part); every part round-trips through `export_step` and the truck reader.

## 9. V — Screenshots and agent-legible views

Owner: `app` (`AgentRender.svelte`, new), `wasm-bridge` (schema). No Rust
geometry work: the data a label needs (`projectFaceCentroids`-style screen
positions, body names, constraint states) is already in the page.

### 9.1 Tool

`viewport_capture` gains arguments; every one optional, so today's call is
unchanged.

| argument | meaning |
|---|---|
| `view` / `camera {position, target, up}` / `frame` / `projection` | the `viewport_view` vocabulary, applied to the capture only; the user's camera never moves |
| `size {width, height}` | fixed output size; the capture renders offscreen at exactly this size |
| `isolate: [body_id \| name]`, `hide: [...]` | visibility for this image only |
| `section {plane}` | the stencil cap at this plane, this image only |
| `style: "shaded" \| "agent"` | `agent` = flat unlit colours, black 2 px edges, enlarged vertices, no antialiasing, fixed background, no hover or selection overlay |
| `color_by: "body" \| "feature" \| "constraint_state" \| "highlight"` + `highlight: [EntityRef]` | semantic colouring; a palette of 24 fixed colours, assigned in sorted-id order |
| `labels: ["body_names", "face_ids", "edge_ids", "dimensions", "constraints", "connectors"]` | overlays drawn as text with leaders |
| `sketch: feature_id` | aligns to the sketch plane, orthographic, draws the sketch with `constraint_state` colouring and dimension labels; nothing else visible unless `isolate` adds it |

Result: the PNG plus `legend: [{color, kind, id, name?}]`, `labels: [{text,
x, y, ref}]`, `camera`, `size`, `style`. An agent reading the image can map
every colour and label back to a reference it can query.

### 9.2 Implementation

A second render pass over the same three.js scene objects, with a settings
override applied for the duration of the pass and restored after: a camera
built from the arguments, `renderer.setSize` to `size` on an offscreen
canvas, antialias off, a replacement material per mesh for `agent` style
(`MeshBasicMaterial` with the legend colour, polygon offset) and the edge
overlay widened, the hover and selection state masked, visibility from
`isolate`/`hide`. Labels are drawn on a 2D canvas over the frame from screen
projections of face centroids, edge midpoints and body AABB tops with a
first-hit visibility test, as `projectFaceCentroids` does today. The viewer
page in server mode answers the same window event, so host mode gets it too.

Constraint-state colouring reads the solver, not the UI heuristic: fully
constrained, under-constrained (points with a non-zero null-space component
from S2), over-constrained (the conflict set), construction, selected. The
heuristic in `recomputeOverConstrained` and `getUnderConstrainedEntities` is
replaced by the same solver data in the editor, which fixes the defect the
survey found.

### 9.3 Determinism oracle

A GUI test captures a corpus case twice in one session and in two browser
sizes with `style: agent`, `size` fixed, and asserts byte-identical PNGs.
Across machines, a perceptual-hash distance under a pinned threshold is the
regression check, and the legend and labels are asserted exactly. The same
test asserts the user's camera, selection and visibility are unchanged after
the call.

### 9.4 V1 as landed

Not `AgentRender.svelte`: the capture stayed on the window event
`AgentCapture.svelte` already answered, because the viewer page answers the
same event (§4.12 of `specs/waffle_server_mode.md`) and a second component
would have given host mode a second implementation. The component only
gathers renderer, scene, live camera, live orbit target and the store's render
list; the pass itself is `app/src/lib/viewport/capture.js`.

- **Framing is shared code, not a second copy.** `app/src/lib/viewport/framing.js`
  holds the standard-view table, the Fit All box, the named-bodies box and the
  fit distance; `CameraControls` moves the user's camera with it and the
  capture builds its throwaway camera with it, so a captured `view` + `fit`
  frames what the View Cube and the F key frame.
- **Arguments:** `view`, `camera {position, target, up?}`, `projection`,
  `fit`, `frame`, `size {width, height}`, `max_edge_px` (the pre-V1 spelling,
  still honoured), `style`, `color_by`, `labels`, `isolate`, `hide`. `fit`
  defaults to true when `view` or `frame` is given and false otherwise, so a
  call with no arguments is still a picture of the live view. `isolate`/`hide`
  are applied BEFORE the fit — "isolate this body and frame it" frames the
  body. Contradictions are refused, not resolved by precedence: `view` with
  `camera`, `color_by` with `style: "shaded"`, the same id in `isolate` and
  `hide`, and `BodyNotFound` for any id the view does not draw.
- **The pass** renders into a `WebGLRenderTarget` of exactly `size` (so
  neither the canvas size nor the device pixel ratio is in the result), with
  every override restored in one `finally` — a refusal cannot leave the user's
  scene recoloured or a body hidden. `agent` style replaces each body's
  material with a flat `MeshBasicMaterial` in its legend colour, which is also
  what keeps hover and selection out of the image; edges go black (rebuilt
  with `withEdgeDepthBias`, since `Material.copy` does not carry
  `onBeforeCompile` and a clone would silently lose the bias), vertices are
  enlarged and flattened to the edge colour, everything that is not a body is
  hidden, and the background is a fixed white. `shaded` re-aims the two
  directional lights from the capture camera's
  quaternion, because `Lighting.svelte` aims them in the LIVE camera's frame
  every frame and a `view: "back"` picture was otherwise lit from the user's
  shoulder. The edge depth bias is set to the capture height for the pass
  (`edgeDepthBias.js`), or a capture smaller than the canvas gets the z-fight
  dashing back.
- **An agent capture holds nothing but the bodies.** The style exists so that
  the legend explains every colour, so the pass hides every drawing object that
  is not a drawn body, its edges or its vertices: the three datum planes and
  the origin triad, the inactive-sketch overlay, the orbit pivot, and whatever
  the viewport grows next (`collectScene`'s `others` bucket is a catch-all, so
  a new component is out of an agent image until someone names it). This was
  not cosmetic. The triad's Z arrow is an OPAQUE mesh along +Z, so for any part
  standing on the XY plane it pierces the top face and paints over it, and the
  datum planes and sketch lines are theme colours that no legend entry names.
  The vertex overlay needed the same treatment from the other direction: it
  bakes the theme's vertex colour AND the user's hover and selection into a
  per-vertex `color` attribute, so it was the one path by which hover still
  reached an agent image; the pass turns `vertexColors` off, sets the edge
  colour and forces opacity 1. Sketches are not a loss — they arrive in V2
  behind the explicit `sketch: feature_id` argument, which is where a caller
  says it wants them. Measured after the change: a `top` capture of two
  extruded boxes contains exactly four colours, `#ffffff` + `#000000` + the two
  legend hexes, and a body's pixels are byte-equal to the hex the legend names
  it by. `agent-capture-views.spec.js` asserts both (the set is closed, and
  each legend colour covers real area); with the hiding removed the same
  assertion reports 22 unexplained colours. `shaded` is untouched: it is a
  picture of the user's viewport, datum planes and all.
- **Antialiasing:** `agent` renders 1:1 — none, by design. `shaded`
  supersamples ×2 and box-filters down, rather than using a multisampled
  render target, whose resolve is not deterministic and whose
  `readRenderTargetPixels` is not portable.
- **Labels** are placed from the capture camera: project the anchor (face
  area-weighted centroid, or the top of a body's box), drop what is
  back-facing or off-frame, drop what fails a first-hit ray against the drawn
  meshes, then sweep nearest-first and drop any box that would overlap one
  already placed. A label dropped is in NEITHER the image nor the array, so
  the two always agree. Each entry is `{kind, text, x, y, body_id, ref}` with
  `ref` the engine's own `GeomRef` for a face — the text is only the key into
  the array, never something to parse.
- **Oracle:** `app/tests/gui/agent-capture-views.spec.js` (5 cases) through the
  page's own executor: the size on `structuredContent` AND on the PNG's IHDR,
  the legend's ids and palette colours, both bodies labelled, exactly one face
  label on a box seen from `top` (the sides are edge-on, the bottom fails the
  first-hit test), `isolate` driving both the legend and the fit, the live
  camera unmoved and two calls agreeing, the pre-V1 call unchanged, and each
  refusal by code.
- **Host mode** gets all of it: the relay forwards the whole `arguments`
  object in `capture_request` and returns the page's own structured answer
  (`viewer.py`), and `link.js` runs the same `VIEWPORT_QUERIES.viewport_capture`.

Left for V2/V3 and recorded here so nothing is silently missing: `section`,
`sketch: feature_id`, `color_by: "constraint_state"` and `highlight` (V2, they
need S2's solver state); the `edge_ids`, `dimensions`, `constraints` and
`connectors` label kinds (refused loudly — by the relay against the schema's
enum, and by the tool layer itself, which has to check the same lists because
the in-page executor validates nothing); the §9.3 byte oracle (V3). And the
"2 px" of §9.1's edge style is NOT achieved — WebGL ignores `linewidth`, so GL
lines are one device pixel; real thickness needs fat lines (`Line2`), which is
its own change to `EdgeOverlay`.

Open items, left deliberately:

- **An `agent` capture of a sketch-only document is blank.** The fit still
  frames the sketch (`fitBoxFor` falls back to it, and the camera is built
  before the style overrides), and then the style hides it. The honest answer
  is probably to refuse, or to frame nothing; either is a §9 decision and
  neither is V1's.
- **`fit` alongside an explicit `camera` reports a `framed` box it did not
  frame.** In perspective the box only sets the orthographic zoom, so the
  camera the caller gave is used unchanged while the answer names a box. Either
  refuse the pair or report `framed: null` there.
- **`onAgentView` still carries its own copy of `frameBoxFor`**
  (`CameraControls.svelte`). The V1 refactor shared the standard-view table,
  the Fit All box and the fit distance, but not this one, so the drift it was
  meant to prevent is still open on the `frame` argument.
- **Host-mode `viewport_view` drops `frame`.** `viewer.py` forwards only `view`
  and `fit`, so a framed region works in page mode and silently fits
  everything through a viewer link. `viewport_capture` does forward the whole
  argument object; `viewport_view` should too.

## 10. S — Sketcher parity

Owner: `sketch-solver` (S1, S2), `waffle-types` (ops types), `feature-engine`
(S3 dispatch), `wasm-bridge` (tools), `app` (S3 UI rewire), `test-harness`
(S4).

### 10.1 S1 — Sketch operations in Rust

Trim, extend, offset, sketch fillet and projection become pure functions in
`sketch-solver/src/ops.rs` on `Sketch` (entities plus constraints), each
returning a `SketchEdit { added, removed, changed, constraints_added }`:

```rust
pub fn trim(s: &Sketch, entity: u32, at: Point2) -> Result<SketchEdit, OpError>;
pub fn extend(s: &Sketch, entity: u32, end: End, to: Option<u32>) -> Result<SketchEdit, OpError>;
pub fn offset(s: &Sketch, chain: &[u32], distance: f64, side: Side) -> Result<SketchEdit, OpError>;
pub fn fillet(s: &Sketch, corner: u32, radius: f64) -> Result<SketchEdit, OpError>;
pub fn project(s: &Sketch, sources: &[ProjectedSource], plane: &Plane) -> Result<SketchEdit, OpError>;
pub fn mirror(s: &Sketch, entities: &[u32], axis: u32) -> Result<SketchEdit, OpError>;
```

The browser's `handleTrimTool`, `offsetChainSegments` and `filletCorner`
become callers of these through a `SketchOp` bridge message, so the UI and
the MCP execute one implementation. This is the structural fix: parity by
construction, not by porting twice. The existing GUI specs
(`sketch-trim-tool`, `sketch-offset-tool`, `sketch-fillet-tool`) are the
acceptance tests for the rewire and must pass unchanged. `mirror` is new on
both sides.

### 10.2 S2 — Solver state

`SolvedSketch` gains `residuals: Vec<f64>` per driving constraint,
`conflicts` always populated (not only on failure), `moved: Vec<(u32,
delta)>` against the input positions, and `free: Vec<FreeDirection { point,
direction }>` from a null-space basis of the final Jacobian (the same QR that
computes `dof`). `Redundant` becomes a distinct verdict: a satisfied system
whose row rank is below its row count names the dependent constraints. The
engine maps conflict and residual indices back to the caller's constraint
array through the reference-dimension filter, once, in Rust, so neither the
UI nor the tool repeats the mapping.

### 10.3 S3 — Tools

| tool | inputs | result |
|---|---|---|
| `sketch_edit` | `feature_id`, `ops: [SketchOp]`, `on_error` | `SketchState` + `ModelDelta` |
| `sketch_solve_state` | `feature_id` | `SketchState` |
| `sketch_create` | unchanged | gains `positions` and the full `SketchState` |

`SketchOp` is a tagged enum: `AddEntity`, `RemoveEntity`, `AddConstraint`,
`RemoveConstraint`, `SetDimension { index, value | expression }`,
`SetConstruction`, `MovePoint { id, to }` (a `Pinned` constraint for one
solve, then dropped: the drag), `Trim`, `Extend`, `Offset`, `Fillet`,
`Project`, `Mirror`. Ops apply in order, one solve at the end, one undo step.
`SketchState = { status, dof, conflicts (caller indices), redundant,
residuals, moved, free, positions, radii, regions }`. Entering sketch mode is
not needed: the engine edits the stored sketch and re-solves, which is what
the parameter re-solve path does today.

### 10.4 S4 — Sketch corpus

`app/tests/cases/sketch/<ID>.waffle` + `<ID>.meta.json` using the empty
second manifest slot (`app/tests/cases/manifest.json`), served by the same
dev API. `SketchOracleExpectations { status, dof, conflicts, redundant,
regions: [{entity_ids, area}], positions_tol }`. Runner
`crates/test-harness/tests/sketch_corpus.rs` replays each case through
`solve_sketch` directly (pure tier) and through `sketch_create` dispatch
(engine tier). Independent oracle: a second rank computation from the
published residual definitions, symbolic Jacobian, the same algebra at a
different implementation, in the reference-parity posture the Yang work uses.
A sketch prospector reuses `prospect/{minimize, promote}` with a generator of
random entity-and-constraint sets; a finding is a disagreement between the
solver's verdict and the independent rank, or a V1 capture whose
constraint-state colouring disagrees with the solver, saved with the image.

## 11. E — Electromechanical integration

Owner: `kicad-pcb` (parse exposure), `feature-engine` (`kicad.rs`),
`wasm-bridge` (tools), `app` (export).

1. **E1 — the rest of the board.** Pad positions, sizes and layers reach
   `ComponentMeta.pads` (today only number and net). Drills become derived
   `Hole` features on the board (K3), so a mounting hole is a hole, a cut and
   a connector with a diameter. Component heights come from the placed board
   STEP occurrences' AABBs (already instanced), falling back to a declared
   default per footprint family with a warning, and are stored per component
   as a `KeepOut { polygon on board plane, height }` zone. Courtyards are
   parsed and used for placeholders, closing the recorded deviation.
2. **E2 — interface file.** `interface_export { assembly_tab?, deliver }`
   writes `<board>.mech-interface.json` (schema pinned under `docs/schema/`):
   board frame in world, outline loops with arcs, holes with diameter and
   spec, per-component reference, footprint, side, position, rotation,
   height zone, pads with position and net, connector mating frames (origin,
   normal, pin-1 direction, derived from the library part when the footprint
   maps to one, else from the pad centroid and board normal), and the
   enclosure-side keep-outs: every enclosure body sectioned at the board's
   top and bottom planes by Q4, as polygons in board coordinates with the
   body's name. Units mm, Y-up as the mechanical side sees it, with the
   `.kicad_pcb` convention stated in the header. A KiCad-side consumer is a
   `pcbnew` Python script in `scripts/kicad/` that reads the file and draws
   the enclosure keep-outs as rule areas and checks the outline and holes
   against `Edge.Cuts`, reporting differences. The file is the "even this
   alone" deliverable the goal document names.
3. **E3 — cable routes as centrelines.** A cable is a `Sketch3d` chain with
   `Fillet` entities at every corner; `sketch3d_get` already reports its exact
   length. `CableRoute` (K1's rule kind) checks every corner is a `Fillet`
   with radius at least `min_bend_radius`, the chain length is at most
   `max_length` minus the two connector depths, and the route keeps
   `min_clearance` (Q1 along the chain's sample points) from every other
   body. No solid is needed to answer "does the stock cable reach without
   strain". A round swept cable body for the picture is B6 S4 (torus
   laterals), a separate kernel increment, and the rule does not wait for it.
4. **E4 — outline and holes back to KiCad.** Step 1 is `export_dxf` of the
   board sketch and hole circles (D1a in `specs/drawings_and_mbd.md`), which
   KiCad imports onto `Edge.Cuts`. Step 2 is an `Edge.Cuts` and
   mounting-hole patch to the `.kicad_pcb`, written by the same `pcbnew`
   script from the interface file, so the Rust side never writes KiCad's
   format. Ownership is per feature and recorded in the interface file
   (`owner: mcad | ecad`), and the derived board features keep their
   `DerivedFeatureReadOnly` refusal on the side that does not own them.

Oracle: round trip the two-sided fixture (`two_sided.kicad_pcb` +
`two_sided.step`) through `kicad_link` → `interface_export` → the `pcbnew`
checker, asserting zero differences; add a rule area and assert it lands at
the sectioned enclosure polygon to `OUTLINE_WELD_M`.

## 13. Pushback on the goal document

Where the tree suggests a different route than the document's wording.

1. **Semantic names need persistent ids first.** "Names survive rebuilds and
   parameter changes" is only true if the thing a name points at survives.
   Face Pids exist and edge and vertex Pids do not. N1 is sequenced after D0
   and names are aliases over Pids, not a parallel naming system that would
   drift from the kernel's own lineage.
2. **Two reference bugs come before any reference feature.** Curved faces
   have no signature and roleless faces resolve to an arbitrary face. Until
   N0, a stable reference to a cylinder bore is not achievable by any amount
   of naming machinery.
3. **Minimum wall thickness is sampled, and says so.** An exact medial axis
   over trimmed quadrics is a research project. Q5 reports the sample
   spacing with every answer and lets a rule ask for a denser sample. A
   result that claims exactness it does not have would be the legacy
   pipeline's failure mode in a new coat.
4. **Interference is the boolean, not a new algorithm.** The kernel's exact
   Intersect is the correct interference test and the one that respects the
   project's analytical-primacy invariant. Its coplanar refusal is the
   contact detector. Building a separate mesh-overlap test would give a second
   answer to disagree with the first.
5. **Fastener checks need a Hole feature.** "Clearance holes, thread
   engagement, head clearance against standard tables" cannot be checked on
   an anonymous cut extrude; the check needs a spec to compare against. K3
   adds `Operation::Hole`, which every mainstream CAD has and which the KiCad
   drill data also wants to land in.
6. **Sheet-metal rules are deferred, machining rules are narrowed.** There is
   no bend, flange or flat-pattern feature, so a sheet-metal rule set would
   check nothing. Machining rules are limited to what the geometry can
   express without fillets: sharp internal corners and pocket reach. When a
   feature family lands, K4's scripted rules are how its rules arrive.
7. **Cables are centrelines.** The check the doser needs (length, bend
   radius, clearance) is answerable from a `Sketch3d` with `Fillet` entities
   today. A round cable body on a 3D path is a kernel increment (B6 S4) and
   is not on the path to the acceptance test.
8. **Captures render offscreen.** The user's viewport is theirs. Moving their
   camera, hiding their bodies or switching their style to take a picture
   would make the agent and the human fight over one view, which the
   server-mode viewer work already decided against. The capture is its own
   pass with its own settings, and it returns a legend so the agent never has
   to read a colour off the image by eye.
9. **Rule sets live in the document and the check runs in the engine.** Both
   open questions resolve the same way: data in the file, code below the
   transport. There is no "browser or server" because the engine is the same
   WASM-or-native crate in both.
10. **The interface file is JSON with a pinned schema, written by Rust, read
    by a `pcbnew` script.** The Rust side never writes `.kicad_pcb`; KiCad's
    own Python API is the correct writer for KiCad's format, and DXF through
    D1a covers the outline before any script exists.
11. **The agent corpus needs a success oracle, and measurements are it.**
    There is no shape-similarity oracle and this spec does not propose one.
    A task passes when its measurements, names and rule check say so. That
    is also what the acceptance test's pass condition says.
12. **Sketch parity is one implementation, not two.** Porting trim, extend
    and offset to Rust and having the browser call them is more work than
    adding tools that reimplement them, and it is the only version where
    parity cannot decay.

## 15. What this is not

- Not a drawing or PMI spec; `specs/drawings_and_mbd.md` owns D0–D4 and
  M1–M3, and this spec consumes D0, D1d, D2 and M1.
- Not a kernel capability spec. Helical sweeps, torus laterals on a 3D path
  and the general sweep's S3/S4 cells belong to `specs/b6_general_sweep.md`.
- Not a replacement for the human designer, and not FEA. A simple bolt-load
  estimate can be a K4 script when someone wants it.
- Not a fillet, chamfer or shell dependency. The machining rule and the
  sketch fillet op are written for a kernel without them.
